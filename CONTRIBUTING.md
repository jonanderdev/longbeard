# Contributing to Long Beard

Read this before changing the catalog, the installer, or a skill we own. What the product is and who it is for: [docs/brief.md](docs/brief.md). The public install story: [README.md](README.md). The router that lands in other projects is generated by `bin/long-beard.js` from [beard.json](beard.json); this repo's [AGENTS.md](AGENTS.md) is that output.

Built for Jon's daily use first, and public on npm. Where the two disagree, daily use wins.

What a person leaves with is the selling point: a Figma file of their own, `DESIGN.md` and `docs/design/` in words, and code checked against the frames. The README leads with this. It says why Long Beard is good and never compares it with another tool by name.

The product is Long Beard. The GitHub repo is `jonanderdev/longbeard`. The npm package is `@jonandev/longbeard`. The command is `longbeard`.

## Stages

| Stage | Runs | Reads → writes |
|---|---|---|
| 1. Idea | `idea` (ours), with Matt's `grilling` | the idea, or the repo → `docs/brief.md` |
| 2. Design | The `design-*` family (ours), entered through `design`: `design-brief` → `design-moodboard` (`design-families` for a big board) → `design-direction` → `design-identity` → `design-prototype` → `design-figma`; `design-content` and `design-wordmark` optional; `design-check` on each frame | brief → `docs/design/design-*.md` → `DESIGN.md`, official → Ready Figma frames |
| 3. Architecture | Matt's `grill-with-docs`, then `framework-skills` (ours) | brief, `DESIGN.md` → `GLOSSARY.md`, ADRs |
| 4. Plan | Matt's `setup-matt-pocock-skills` (once), `to-spec`, `to-tickets` | brief flows → specs → tickets |
| 5. Build | Matt's `implement-spec` → Matt's `tdd` → `design-check` build mode → Matt's `pr` | tickets → failing tests first → one PR per spec; Jon merges |

- Every stage writes one file the next stage reads. No stage depends on chat history, so any stage can start once its input exists and an existing project can join mid-pipeline. A stage whose file already exists is done: a project with a `DESIGN.md` goes from its brief to Architecture.
- Some of Matt's skills can only be started by the person, as he publishes them (`grill-with-docs`, `to-spec`, `to-tickets`, `implement-spec`). The router and our skills say to type the command rather than promise to start them.
- No UI (CLI, API, library): the brief says so, and Design is skipped.
- A graphic (a poster, a card or invitation, a social post): the brief says so, and Design runs on the same steps with what differs in each skill's `references/graphic.md`. Its run ends at the exported Figma frame: nothing offers Architecture, Plan or Build. Sites and apps stay the main use, and their run is unchanged. A single piece is proved first (a poster); a card and a post follow the same path.
- After the first pass, a feature loops: grill it (`grill-with-docs` when it brings new terms, so they land in `GLOSSARY.md`; plain `grilling` otherwise) → `design-moodboard` for one piece, if needed → `design-prototype` (prototype optional) → Plan → Build. Identity and Architecture rerun only for a rebrand or a new stack.
- Long Beard owns everything before code. Matt Pocock's kit owns code, as he publishes it. Figma's skills own Figma mechanics. We do not rewire a step inside their flows.

## What each stage promises

The rules live in each skill's SKILL.md. Change them there. This is what the product promises.

**Idea.** `docs/brief.md` is one page with fixed headings that later stages read by name. No tech choices and no look. Features get specs, not brief edits; the brief changes only when the product does. An existing project gets a draft from its documents and code, then questions on the gaps.

**Design.** A family of small skills, each with one job, one doc and few stops, so a person runs only what they need and a run never drifts. Each reads its inputs from files, never from the chat before it, says at its top what it **Needs**, **Uses if there** and **Writes** (a test keeps those consistent across the family), says what it needs when that is missing, and ends by naming the next step. `design` is the way in: it reads the project and suggests the next skill with the reason, offers `design-families` only for a board over about 60 references, and never runs a skill on its own. **They are the designer; the agent has no taste and claims none.** An AI's taste is an average of what once looked good, or a skill author's own; this flow carries the person's instead: the references they pick, what they like in each, the calls a designer makes, all on rendered options, never in words. The agent does the craft: it rebuilds their references faithfully with the real content, combines what they took from each, checks that it still works, and adds nothing that is not on their board. It never picks, drops or ranks what it shows. Every change to a design skill is judged by this: does it carry their taste further, or put the model's in its place? Each stop says what is new and asks one question, in a few lines.

- **design-brief:** a studio's questions in one message, each with a suggested answer and never a look; one read-back.
- **design-moodboard:** their board is the pool and is never cut to a number; a gap gets a search sized to it. With no board, a wide search they mark like or no. A like from a site or app keeps up to four of that product's other screens (`also`), never marked, so the other key screens can follow how one product carried its look.
- **design-families** (optional): a big board sorted into measured looks, which become the headings of the board they choose from. Nothing is dropped: references span families. Their own board is never touched.
- **design-direction:** eight first screens, each one reference rebuilt faithfully with the product's content, then changed by one or two moves borrowed from others. What they like is what is borrowed; their why is where it may go; what they say to leave out of a reference is never on a screen. Nothing comes from outside the board: no face, colour, gradient, shadow, radius, button style or effect none of their references has. One agent builds the screens itself, with no helpers or judges: side by side on two boards, this short method held up against the heavier flow at about a tenth of the tokens. Scripts check contrast and clipped text; a check reports, and the concept wins. They choose on a canvas that shows each screen beside what it is made from; parts are opened only when they ask.
- **design-identity:** the chosen screen's type and colours refined on that screen, from options that trace to the references, the subject or what they own, never invented by the agent, with a few live controls bounded by the board; the identity board.
- **design-prototype:** the first screen finished, then the other key screens and their states with real copy. The chosen screen is the frame as a system (header, navigation, grid, type sizes, colour roles, spacing), never a composition to repeat: each page opens with its own job, and its content may take a layout from a reference that shows that kind of content, inside the frame. Checks are scripts only (contrast, rules, drift, links), and a check never undoes the concept. Stand-ins are marked and listed under Still to supply. `DESIGN.md` is written on their yes to the rendered prototype; its tables are the source, and its token block is generated from them. A feature adds to `DESIGN.md` and never rewrites it; an identity change needs its own yes.
- **design-figma:** our tokens, never a community kit; every key screen and reachable state, faithful to the prototype, marked Ready on their yes. Figma is the truth for screens; `DESIGN.md` is the written summary. Figma is required for UI projects.
- **design-content** (optional, any time): each key screen's job, real copy and pictures, drafted for them to correct.
- **design-wordmark** (optional, after the identity): a mark from the identity's faces and devices, judged in the chosen screen. No mark is a fine answer.

**Two folders.** `docs/design/` is committed and kept up to date. It describes the style, never a source: no site, brand, studio, designer, person or link from the references, and no path into the working folder. `.longbeard/design/` is the agents' working folder (captures, pickers, profiles, grids, prototypes), gitignored, and may not survive a cloud session: the docs carry the meaning. `DESIGN.md`, Figma, code, commits, PRs, specs and tickets never name a reference either. Sources are only ones checked to work without a login.

**design-check.** Checks a screen against `rules/design-rules.md` and `DESIGN.md`, and reports. It never redesigns. Frame mode runs after each Figma screen; build mode compares the built screen with its Ready frame on meaning, not pixels; docs mode finds a reference named, or values that disagree. Hard findings block for one fix pass and one re-check, and what remains goes in the PR; soft ones are reported. Anything lost or changed from the approved prototype without a yes is hard. A state or theme it could not see is "not checked", never passed.

**Design rules.** `rules/design-rules.md` is our own text: an Idea check, then 14 sections of checks you can pass or fail from a screenshot, a site list, an app list, and dated tells. Hard rules (structure, contrast, targets, focus, states) are the floor. Soft rules can be overridden in `DESIGN.md` on purpose, with a reason. The rules never suggest a look.

**Architecture, Plan, Build.** Matt's skills, as he publishes them. `GLOSSARY.md` is born at Architecture, seeded from the brief and the copy already in the Figma screens, so it records the words the product uses. Renaming a term the screens already show is a question, never silent. `codebase-design` shapes module interfaces. The first pass writes one spec per core flow, later one spec per feature, on the tracker `setup-matt-pocock-skills` chose. `implement-spec` runs as published: an integration branch, a fresh agent per ticket, `tdd` on every ticket (its acceptance criteria become failing tests before any code; the router names it in the Build row, not as an ask), `code-review` at the end, one PR per spec. `pr` writes the body, and design-check's evidence goes in its Before/After.

**framework-skills.** Runs after `grill-with-docs` at Architecture, and again when the repo gains a stack (a new manifest or framework). It reads the stack from the ADRs and manifests, skips what already has a skill or was declined, and searches with the pinned Skills CLI (`skills find`): the framework's own organisation first, else the most installed. It reads each `SKILL.md` before proposing, proposes only the ones this project will use, and installs on yes with `longbeard add`, so they land in `beard.local.json` and refresh on `update`. A no is one line in the stack's ADR. It never writes a skill and never vendors one.

**Where files live.** `DESIGN.md` and `GLOSSARY.md` at the root, `docs/brief.md`, ADRs in `docs/adr/`. These are Matt's defaults: `setup-matt-pocock-skills` records them in `docs/agents/domain.md`, and `code-review` searches the repo for its standards, so ADRs are found without anything of ours.

**Glue.** UI tickets link their Ready Figma frame. UI work follows `DESIGN.md` and that frame; a mismatch is a bug.

## Shape

- Curated catalog in `beard.json`: `stages` (the router's table) and `items` (optional `kind`, default `skill`). An item with `"kit": true` is an author's whole published set: the skills in their plugin manifest, else every folder in their `skills/`. Its `routes` are the router's helper lines. An item with `"via"` is suggested by that skill, so the router gives it no line (the design family, through `design`). Skills stay with their authors. Do not vendor other people's skills.
- Kit: Long Beard's thirteen (`idea`, the ten `design-*` skills with `design` as their way in, `design-check`, `framework-skills`), Matt Pocock's whole kit as one entry, Figma's four (`figma-use`, `figma-generate-library`, `figma-generate-design`, `figma-design-to-code`). Add-ons are `optional`: they install with `--skill <name>` or `--all`, and the router offers each one once, when it is needed. A taken add-on stays and refreshes. An add-on marked `preselected` is ticked at `init` instead: it is decided there, so the router never offers it, and a project that turned it down is not asked again. Only `modern-web-guidance` is, because most projects here are web.
- Shapes: `init` installs the whole pipeline, or a shape `beard.json` names under `shapes`. The one shape is `design` (design only): `items` it lists (`idea`, `design`, `design-check`, `figma-use`, `figma-generate-library`, `figma-generate-design`) plus whatever they suggest through `via` (the design family), the `addons` it offers (`jury`), its own `stages` (Idea, and Design with `design-check` added), and the two router paragraphs in `notes`. Build, Plan, Architecture, Matt Pocock's kit, `figma-design-to-code` and the code add-ons are left out. It is one choice, not a second package: `--design` at `init`, or on a first `init` in a terminal the question "Design only, or the whole pipeline?". `beard-lock.json` records `"shape": "design"` (absent means the whole pipeline); `update` filters the catalog by it, so it adds new skills inside the shape and none outside, and its retiring still reads the whole catalog. `init --full` or `update --full` widens it and clears the shape; `--design` on a project that already has the whole pipeline stops. The design-only router still fits the 200-word limit, and `npm test` checks that it names no skill the shape does not install.
- Runtime: the installer needs Node 18. The scripts in the skills need Node 22 and Chrome, and `design-figma` needs the Figma connection; the README says so.
- Installer: `bin/long-beard.js`. Pins Skills CLI `skills@1.7.2`. `init` asks which agents on a TTY (catalog defaults pre-checked), then which add-ons (`preselected` ones pre-checked). `--all`, `--skill` and `--no-addons` answer the second question and skip it. Without a TTY, or with `--yes`, a first `init` takes the pre-checked add-ons; a later `init` takes none, so a refusal holds. `--agent` skips the list and installs for that tool. `--yes` uses the catalog agents.
- One block in the project's `AGENTS.md`, between `<!-- longbeard:start -->` and `<!-- longbeard:end -->`. The kit block is under 200 words, and `npm test` checks it. Each add-on a project takes adds a line, a preselected one included, so a first `init` writes a little over 200. Do not write `CLAUDE.md` or Copilot files unless asked.
- Local skills live under `skills/` with `"source": "local"` and ship with the package. A new skill we own is another folder here, not another package. Files more than one of them needs (`rules/design-rules.md`, `capture.mjs`, `contrast.mjs`, `sheet.mjs` and the rest listed in `scripts/share.mjs`) have one source and are copied in by `npm run share`; `npm test` fails on drift. Edit the source, never a copy.
- A project can omit or add skills in `beard.local.json`. Init is blocked inside this repository.
- `beard-lock.json` records a content hash per skill. `update` treats a skill as edited when its files differ from that hash. It removes any skill the catalog or its kit no longer lists, unless edited; `--force` removes edited ones too.
- Do not edit `AGENTS.md` by hand. Change the generator or `beard.json`, then `npm run router`. `add` and `remove` in this repo rewrite it. `npm test` fails when the two drift, and `scripts/release.sh` runs it.

Few skills. Few tokens. A kit or skill that stops earning its place is dropped. The design family is many skills on purpose: each is small and loaded alone, so a run reads far less than one long skill did.

`kind` is the door to grow past skills later. Until a new kind has an installer, do not catalog it. MCP servers are not a `skill` and `init` cannot wire them yet.

Do not put model-picker warnings in the kit. A skill that needs the current year should say so.

## How to know it worked

Installed ≠ used. There is no usage logger. Judge the files: each stage's file appears only after its yes (`docs/brief.md`, the `docs/design/design-*.md` docs, `DESIGN.md`, Ready frames, specs, tickets, a PR); `design-check` docs mode finds no reference named in `docs/design/` or `DESIGN.md`; `screens.json` gives every screen a base and moves from references on the board; Ready frames have their states; the PR carries design-check's shots and findings.

The design skills have a repeatable run of their own: `eval/design/` builds a fixed project (a bakery's brief, ten references, the person's answers at every stop), runs an agent from `design` to `DESIGN.md`, and scores what it left with the checks above (`eval/design/README.md`). Before a release that carries a design change, run the short one: `run.mjs --short` builds the direction's first round from fixed readings, offline, and scores it, in about 15 minutes. Run it in full only after a big change to the Design stage (a skill added, dropped or reordered, or a change to the moodboard or the readings), and then freeze its readings for the short run (`freeze.mjs`). After any other design change, the tests are enough to merge.

Smoke project: `../longbeard-smoke`, outside this git tree; create it there (a fresh folder, `init` run in it) if it is missing. After changing a local skill, copy `skills/<name>/` into that project's `.agents/skills/<name>/` (and `.claude/skills/` if present) and replace the `AGENTS.md` block with the output of `node bin/long-beard.js router`. A full smoke run starts fresh: one idea through brief, design brief, moodboard, direction, identity, screens, `DESIGN.md` and a Figma key screen, then one small spec through Build and `design-check`. Do not run `longbeard init` in *this* repo.

## Do not

- Discuss skills in the README that are not in the catalog.
- Treat an award gallery as a style to copy (gates, WebGL, custom cursors). References give patterns.
- Monitor skill use, or add competing design builders, "for completeness."

## Releases

Outside users install the npm version. `main` can move between tags. Do not tell them to install `github:jonanderdev/longbeard`.

A release is one number in three places: `package.json`, the git tag `vX.Y.Z`, and npm. The notes are the matching section of `CHANGELOG.md`. GitHub release notes are that section, not a second writeup.

`CHANGELOG.md` and the README say what a person who installed the package can do. They do not describe how a release is cut.

Change the number by hand, and only in that release commit. A push to `main`, and a pull request into `main`, do not get a new version. Those commits stack under `Unreleased` in `CHANGELOG.md`. Ship a version when someone who already ran `init` should take the new copy: the installer, the catalog, a skill in this repo, or the public install story. A wording fix can wait for that release. Do not add a bot that publishes on every merge.

1. Review the tells in `rules/design-rules.md`: add new ones, retire stale ones, update the date, run `npm run share`.
2. If it carries a design change, the short eval passes: `node eval/design/run.mjs --short --out <folder outside the repo> --agent …` (`eval/design/README.md`).
3. Write what changed under a heading `## X.Y.Z — date` in `CHANGELOG.md`. Include what a person who already ran `init` must do.
4. Set that same number in `package.json`.
5. Commit that, and merge it into `main`.
6. Start `.github/workflows/release.yml` on `main`: Actions, release, Run workflow (an agent can start it too). Pushing the tag `vX.Y.Z` with `./scripts/release.sh` starts it as well.

The workflow checks that the tag (when one was pushed), `package.json` and a `CHANGELOG.md` section agree and that npm does not have the version, runs `npm test`, publishes with provenance, and makes the GitHub release from that section, which creates the tag when the run was started by hand. It stops at the first of those that fails. npm trusts the workflow by name (Trusted Publisher on npmjs.com, set once by the package's owner), so no npm token is stored in the repo or on GitHub; never add one. `./scripts/release.sh` runs the same checks before it tags, so a bad tag is caught on your machine. After a publish the site can lag: check with `npm view @jonandev/longbeard version` before trying a number again. Do not publish that number again.

The workflow publishes only when someone starts it or pushes a tag, never on a merge. It is there so npm can show each version was built from its tag.

While the version is `0.x`, a patch does not change the kit. A minor can add, drop, or change a skill or a flag.

`update` refreshes other people's skills from their current repositories. A Long Beard version pins the skills in this repo and the `AGENTS.md` block. It does not pin Matt's kit, Figma's skills, or the add-ons.

`0.0.0-stage` was a registry check. It is not a release. Deprecate it when convenient: `npm deprecate @jonandev/longbeard@0.0.0-stage "Registry check. Install 0.1.0 or later."`
