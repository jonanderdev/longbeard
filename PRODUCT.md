# Long Beard — what this is

Read this before changing the catalog, the installer, or a skill we own. The public install story is [README.md](README.md). The router that lands in other projects is generated by `bin/long-beard.js` from [beard.json](beard.json); this repo's [AGENTS.md](AGENTS.md) is that output.

## Job

A pipeline for agents you already use (Cursor, Claude Code, and the rest): start in a fresh project with an idea and end with reviewed pull requests. The router tells the agent which stage it is in from the files that exist, and each stage ends by offering the next. Two commands: `init`, then later `update`.

Public on npm, built for Jon's daily use first. Where the two disagree, daily use wins.

It is not an agent runtime. It is not a marketplace. It is not a replacement for Cursor or Claude commands. It is not a way to get a finished page from one prompt.

## Who it is for

People who design, or who care how their product looks, and want work they can deliver. The design stage works the way a studio does: it asks the questions a design director asks, reads their references, shows rendered options, and waits for their choice at each step. That asks for some of their time on purpose, and the steps are never cut down to remove their choices.

- With a brand or a moodboard: those go in first, and the agent fills only what is missing.
- With nothing yet: the agent searches, and they mark what they like. Their picks are the board.

What they leave with is the selling point: a Figma file of their own (variables, styles, the identity board, components, every key screen with its states) that they keep changing by hand or with their agent, `DESIGN.md` and `docs/design/` in words, and code checked against the frames. The README leads with this. It says why Long Beard is good and never compares it with another tool by name.

The product is Long Beard. The GitHub repo is `jonanderdev/longbeard`. The npm package is `@jonandev/longbeard`. The command is `longbeard`.

## Stages

| Stage | Runs | Reads → writes |
|---|---|---|
| 1. Idea | `idea` (ours), with Matt's `grilling` | the idea, or the repo → `docs/brief.md` |
| 2. Design | The `design-*` family (ours), entered through `design`: `design-brief` → `design-moodboard` (`design-families` for a big board) → `design-direction` → `design-identity` → `design-prototype` → `design-figma`; `design-content` and `design-wordmark` optional; `design-check` on each frame | brief → `docs/design/design-*.md` → `DESIGN.md`, official → Ready Figma frames |
| 3. Architecture | Matt's `grill-with-docs`, plus a framework add-on | brief, `DESIGN.md` → `GLOSSARY.md`, ADRs |
| 4. Plan | Matt's `setup-matt-pocock-skills` (once), `to-spec`, `to-tickets` | brief flows → specs → tickets |
| 5. Build | Matt's `implement-spec` → `design-check` build mode → Matt's `pr` | tickets → one PR per spec; Jon merges |

- Every stage writes one file the next stage reads. No stage depends on chat history, so any stage can start once its input exists and an existing project can join mid-pipeline. A stage whose file already exists is done: a project with a `DESIGN.md` goes from its brief to Architecture.
- Some of Matt's skills can only be started by the person, as he publishes them (`grill-with-docs`, `to-spec`, `to-tickets`, `implement-spec`). The router and our skills say to type the command rather than promise to start them.
- No UI (CLI, API, library): the brief says so, and Design is skipped.
- After the first pass, a feature loops: grill it (`grill-with-docs` when it brings new terms, so they land in `GLOSSARY.md`; plain `grilling` otherwise) → `design-moodboard` for one piece, if needed → `design-prototype` (prototype optional) → Plan → Build. Identity and Architecture rerun only for a rebrand or a new stack.
- Long Beard owns everything before code. Matt Pocock's kit owns code, as he publishes it. Figma's skills own Figma mechanics. We do not rewire a step inside their flows.

## What each stage promises

The rules live in each skill's SKILL.md. Change them there. This is what the product promises.

**Idea.** `docs/brief.md` is one page, about 500 words, with fixed headings later stages read by name: problem, who it is for, 3–5 flows, 2–4 key screens, surface (site, app, or no UI), v1 and later, constraints, position (what it is up against, what it is remembered for, its personality), identity nouns, out of scope. No tech choices. Features get specs, not brief edits; the brief changes only when the product does. An existing project gets a brief drafted from its documents and code, then grilled on the gaps, and is asked what happens to any document that now covers the same ground.

**Design.** A family of small skills, each with one job, one doc and few stops, so a person runs only what they need and a run never drifts. Each reads its inputs from files, never from the chat before it, says at its top what it **Needs**, **Uses if there** and **Writes** (a test keeps those consistent across the family), says what it needs when that is missing, and ends by naming the next step. `design` is the way in: it reads the project and suggests the next skill with the reason, offers `design-families` only for a board over about 60 references, and never runs a skill on its own. **They are the designer; the agent has no taste and claims none.** An AI's taste is an average of what once looked good, or a skill author's own; this flow carries the person's instead: the references they pick, what they like in each, the calls a designer makes, all on rendered options, never in words. The agent does the craft: it rebuilds their references faithfully with the real content, combines what they took from each, checks that it still works, and adds nothing that is not on their board. It never picks, drops or ranks what it shows. Every change to a design skill is judged by this: does it carry their taste further, or put the model's in its place?

- **design-brief:** one message of a studio's questions, each with a suggested answer from the brief and never a look (takeaway, personality sliders, feel and never, loves, apart from, what is fixed, motion picked from options and never one word, an existing moodboard); one read-back; `docs/design/design-brief.md`. The sites they love are kept privately for the search.
- **design-moodboard:** their board is the pool and is never cut to a number; a gap gets a search sized to it. Without one, a wide search they mark like or no on a picker, twice at most. Big Figma boards: scope asked first, their captions, tags and stars read from nodes, shared sheets downloaded once and cropped. Keeps are captured at full size, motion as recorded frames. Each keep gets its move in words. `design-moodboard.md` says what the board holds, the moves, the noes and what is missing.
- **design-families** (optional): every keep measured and tagged, sorted by script, split, merged and named by eye, a bin broken up, strays placed. A Figma board gets a `Families` page of copies; theirs is never touched. They take one or two families.
- **design-direction:** works from the references the way a designer works from a board. First, three or four pictures of the product's own subject (theirs, or clearly licensed stand-ins from Wikimedia Commons via `pictures.mjs`, a few and never a bulk search). Then the order the screens are filled in (the primary action, the status, what the product shows), headlines that say the takeaway, the ownable; they lead and like 6 to 10 references and say, for each, what they like in it and why. Each reference is read and measured (`measure.mjs`, `fonts.mjs --shape` for a picture): layout, type, spacing, palette, picture treatment, slots, devices. Eight screens: each one reference rebuilt faithfully with the product's content (kept, and checked beside it), then changed by one or two moves borrowed from other references: what they like is what is borrowed, and their why is where it may go. Five principles decide every case: the base stands unless a move names it; every measure is a share of the screen and is kept; a borrowed thing keeps its geometry and its why; a move changes only what it names; nothing from outside the board. Each screen is made by fresh agents with one job each: a builder translates the base (measured against it with `layout-diff.mjs`) and makes the moves; a critic, with only the pictures, lists every spot where the screen is less finished than its reference, each shown in the reference; a fixer changes only those spots, toward the reference; again until a critic finds nothing, at most three times. Then the round: not a copy, as varied as the board, contrast (a failure blocks the sheet), faults. They pick, ask for more of one, a mix, or a fresh round. On the chosen screen, a touch-up pass repairs only: contrast where text sits, a missing item or action, something plainly broken, a headline outranked by smaller text; shown before and after. Overlaps, collisions and crops the references use are the look and are never tidied. `design-direction.md` describes the composition, its hierarchy, what it carries and what waits for the prototype, and the type and colours as built.
- **design-identity:** refines the chosen screen's type and colours on that screen: three to five pairings (as built, measured neighbours from `fonts.mjs` with at least two beyond the most used, faces of their other references) and palettes (as built, even OKLCH steps from `colours.mjs`, their references, the subject's pictures, theirs), all rendered on the chosen screen and contrast-checked, never invented by the agent; one refinement; the identity board (`design-identity.html`: faces at size, squircle swatches with values and roles). `design-identity.md` holds the values and a `json identity` block, set back on the chosen screen through its `LOOK`.
- **design-prototype:** the first screen finished (faces, spacing chosen on a crop, detail, every width, motion replayed from references, the ownable, states, themes), then the other key screens in one go with drafted real copy and the product's own pictures, options only where a layout forks. Anything the product does not really have yet (a stand-in picture, an assumed price, hour, number or name) is marked `data-standin` in the markup; `links.mjs` lists it, the list is shown with the prototype and kept in `DESIGN.md` under Still to supply for Figma and `design-check`. A pattern that brings a feature the brief lacks goes back to Idea. On their yes to the rendered prototype, `DESIGN.md` in one go, contrast-checked. A feature adds to `DESIGN.md` and never rewrites it; an identity change needs its own yes.
- **design-figma:** our tokens, never a community kit; the identity board on the Cover, bound to the variables; only the components the key screens need; every screen and reachable state (one nobody can reach recorded as not needed); themes as modes; faithful to the prototype; `design-check` on each; `… — Ready` on their yes. Figma is the truth for screens; `DESIGN.md` is the written summary. Figma is required for UI projects.
- **design-content** (optional, any time): per key screen, its job, first read, sections with real copy, actions, pictures and states, drafted for them to correct; stand-ins found only for the pictures still missing.
- **design-wordmark** (optional, after the identity): four to six marks from the identity's faces and devices, the plain name among them, judged where the name sits in the chosen screen; one push; SVG in `docs/design/`. No mark is a fine answer, and a screen whose composition leaves the name out keeps it out.

**Two folders.** `docs/design/` is committed and kept up to date. It describes the style, never a source: no site, brand, studio, designer, person or link from the references, and no path into the working folder. `.longbeard/design/` is the agents' working folder (captures, pickers, profiles, grids, prototypes), gitignored, and may not survive a cloud session: the docs carry the meaning. `DESIGN.md`, Figma, code, commits, PRs, specs and tickets never name a reference either. Sources are only ones checked to work without a login.

**design-check.** Checks a screen against `rules/design-rules.md` and `DESIGN.md`, and reports. It never redesigns. Frame mode runs after each Figma screen; build mode renders the built screen at phone and desktop, in each theme, and compares it with its Ready frame on meaning (structure, tokens, copy, states), not pixels. Hard findings block: one fresh fix pass, one re-check, and what remains goes in the PR. Soft findings are reported. Anything lost or changed from the approved prototype without a yes is a hard finding. It finds states by what a frame shows, not its name. A state or theme it could not see is "not checked", never passed. Docs mode checks that the design docs name no reference and that the identity's values agree.

**Design rules.** `rules/design-rules.md` is our own text: an Idea check, then 14 sections of checks you can pass or fail from a screenshot, a site list, an app list, and dated tells. Hard rules (structure, contrast, targets, focus, states) are the floor. Soft rules can be overridden in `DESIGN.md` on purpose, with a reason. The rules never suggest a look.

**Architecture, Plan, Build.** Matt's skills, as he publishes them. `GLOSSARY.md` is born at Architecture, seeded from the brief and the copy already in the Figma screens, so it records the words the product uses. Renaming a term the screens already show is a question, never silent. `codebase-design` shapes module interfaces. The first pass writes one spec per core flow, later one spec per feature, on the tracker `setup-matt-pocock-skills` chose. `implement-spec` runs as published: an integration branch, a fresh agent per ticket, `tdd`, `code-review` at the end, one PR per spec. `pr` writes the body, and design-check's evidence goes in its Before/After.

**Where files live.** `DESIGN.md` and `GLOSSARY.md` at the root, `docs/brief.md`, ADRs in `docs/adr/`. These are Matt's defaults: `setup-matt-pocock-skills` records them in `docs/agents/domain.md`, and `code-review` searches the repo for its standards, so ADRs are found without anything of ours.

**Glue.** UI tickets link their Ready Figma frame. UI work follows `DESIGN.md` and that frame; a mismatch is a bug.

## Shape

- Curated catalog in `beard.json`: `stages` (the router's table) and `items` (optional `kind`, default `skill`). An item with `"kit": true` is an author's whole published set: the skills in their plugin manifest, else every folder in their `skills/`. Its `routes` are the router's helper lines. An item with `"via"` is suggested by that skill, so the router gives it no line (the design family, through `design`). Skills stay with their authors. Do not vendor other people's skills.
- Kit: Long Beard's twelve (`idea`, the ten `design-*` skills with `design` as their way in, `design-check`), Matt Pocock's whole kit as one entry, Figma's four (`figma-use`, `figma-generate-library`, `figma-generate-design`, `figma-design-to-code`). Add-ons are `optional`: they install with `--skill <name>` or `--all`, and the router offers each one once, when it is needed. A taken add-on stays and refreshes. An add-on marked `preselected` is ticked at `init` instead: it is decided there, so the router never offers it, and a project that turned it down is not asked again. Only `modern-web-guidance` is, because most projects here are web.
- Shapes: `init` installs the whole pipeline, or a shape `beard.json` names under `shapes`. The one shape is `design` (design only): `items` it lists (`idea`, `design`, `design-check`, `figma-use`, `figma-generate-library`, `figma-generate-design`) plus whatever they suggest through `via` (the design family), the `addons` it offers (`jury`), its own `stages` (Idea, and Design with `design-check` added), and the two router paragraphs in `notes`. Build, Plan, Architecture, Matt Pocock's kit, `figma-design-to-code` and the code add-ons are left out. It is one choice, not a second package: `--design` at `init`, or on a first `init` in a terminal the question "Design only, or the whole pipeline?". `beard-lock.json` records `"shape": "design"` (absent means the whole pipeline); `update` filters the catalog by it, so it adds new skills inside the shape and none outside, and its retiring still reads the whole catalog. `init --full` or `update --full` widens it and clears the shape; `--design` on a project that already has the whole pipeline stops. The design-only router still fits the 200-word limit, and `npm test` checks that it names no skill the shape does not install.
- Runtime: the installer needs Node 18. The scripts in the skills need Node 22 and Chrome, and `design-figma` needs the Figma connection; the README says so.
- Installer: `bin/long-beard.js`. Pins Skills CLI `skills@1.7.2`. `init` asks which agents on a TTY (catalog defaults pre-checked), then which add-ons (`preselected` ones pre-checked). `--all`, `--skill` and `--no-addons` answer the second question and skip it. Without a TTY, or with `--yes`, a first `init` takes the pre-checked add-ons; a later `init` takes none, so a refusal holds. `--agent` skips the list and installs for that tool. `--yes` uses the catalog agents.
- One block in the project's `AGENTS.md`, between `<!-- longbeard:start -->` and `<!-- longbeard:end -->`. The kit block is under 200 words, and `npm test` checks it. Each add-on a project takes adds a line, a preselected one included, so a first `init` writes a little over 200. Do not write `CLAUDE.md` or Copilot files unless asked.
- Local skills live under `skills/` with `"source": "local"` and ship with the package. A new skill we own is another folder here, not another package. Files more than one of them needs (`rules/design-rules.md`, `capture.mjs`, `contrast.mjs`, `sheet.mjs` and the rest listed in `scripts/share.mjs`) have one source and are copied in by `npm run share`; `npm test` fails on drift. Edit the source, never a copy.
- A project can omit or add skills in `beard.local.json`. Init is blocked inside this repository.
- `beard-lock.json` records a content hash per skill. `update` treats a skill as edited when its files differ from that hash. It removes any skill the catalog or its kit no longer lists, unless edited; `--force` removes edited ones too.
- Do not edit `AGENTS.md` by hand. Change the generator or `beard.json`, then `npm run router`. `add` and `remove` in this repo rewrite it. `npm test` fails when the two drift, and `scripts/release.sh` runs it.

Few skills. Few tokens. A kit or skill that stops earning its place is dropped. The design family is many skills on purpose: each is small and loaded alone, so a run reads far less than one long skill did.

`kind` is the door to grow past skills later. Until a new kind has an installer, do not catalog it. MCP servers are not a `skill` and `init` cannot wire them yet.

Do not put model-picker warnings in the kit. A skill that needs the current year should say so.

## How to know it worked

Installed ≠ used. There is no usage logger. Judge the files: each stage's file appears only after its yes (`docs/brief.md`, the `docs/design/design-*.md` docs, `DESIGN.md`, Ready frames, specs, tickets, a PR); `design-check` docs mode finds no reference named in `docs/design/` or `DESIGN.md`; `screens.json` gives every screen a base and moves from references on the board; Ready frames have their states; the PR carries design-check's shots and findings.

The design skills have a repeatable run of their own: `eval/design/` builds a fixed project (a bakery's brief, ten references, the person's answers at every stop), runs an agent from `design` to `DESIGN.md`, and scores what it left with the checks above (`eval/design/README.md`). Run it before merging a change to a design-* skill.

Smoke project (outside this git tree): `../longbeard-smoke`. After changing a local skill, copy `skills/<name>/` into that project's `.agents/skills/<name>/` (and `.claude/skills/` if present) and replace the `AGENTS.md` block with the output of `node bin/long-beard.js router`. A full smoke run starts fresh: one idea through brief, design brief, moodboard, direction, identity, screens, `DESIGN.md` and a Figma key screen, then one small spec through Build and `design-check`. Do not run `longbeard init` in *this* repo.

## Do not

- Discuss skills in the README that are not in the catalog.
- Treat an award gallery as a style to copy (gates, WebGL, custom cursors). References give patterns.
- Monitor skill use, or add competing design builders, "for completeness."

## Releases

Outside users install the npm version. `main` can move between tags. Do not tell them to install `github:jonanderdev/longbeard`.

A release is one number in three places: `package.json`, the git tag `vX.Y.Z`, and npm. The notes are the matching section of `CHANGELOG.md`. GitHub release notes are that section, not a second writeup.

`CHANGELOG.md` and the README say what a person who installed the package can do. They do not describe how a release is cut.

Change the number by hand, and only in that release commit. A push to `main`, and a pull request into `main`, do not get a new version. Those commits stack under `Unreleased` in `CHANGELOG.md`. Ship a version when someone who already ran `init` should take the new copy: the installer, the catalog, a skill in this repo, or the public install story. A wording fix can wait for that release. Do not add a bot that publishes on every merge.

1. Review the tells in `rules/design-rules.md`: add new ones, retire stale ones, update the date, run `npm run share`.
2. Write what changed under a heading `## X.Y.Z — date` in `CHANGELOG.md`. Include what a person who already ran `init` must do.
3. Set that same number in `package.json`.
4. Commit that, and push `main`. Stay on that commit.
5. From the repo root, run `./scripts/release.sh`.

The script runs `npm test`, reads `package.json`, tags that number, and publishes it. It does not rewrite `CHANGELOG.md`. It stops if a test fails, if that section is missing, if the tag exists, or if npm already has the version. After `npm publish`, the site can lag. If the next attempt says the version is already staged, wait and run `npm view @jonandev/longbeard version`. Do not publish that number again.

There is no publish workflow. A GitHub Action would earn its place only to prove the package was built from that tag. Until then, do not add one.

While the version is `0.x`, a patch does not change the kit. A minor can add, drop, or change a skill or a flag.

`update` refreshes other people's skills from their current repositories. A Long Beard version pins the skills in this repo and the `AGENTS.md` block. It does not pin Matt's kit, Figma's skills, or the add-ons.

`0.0.0-stage` was a registry check. It is not a release. Deprecate it when convenient: `npm deprecate @jonandev/longbeard@0.0.0-stage "Registry check. Install 0.1.0 or later."`
